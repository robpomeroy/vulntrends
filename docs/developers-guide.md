# VulnTrends developer's guide

This guide is for **developers** working on the VulnTrends codebase - the people
who build the site, add data sources, fix parsers, and change the dashboard. It
complements the other docs:

- [`publishing.md`](publishing.md) - operator runbook for deploying and
  refreshing data on the deployment server.
- [`analyst-guide.md`](analyst-guide.md) - the data schema, pipeline, and
  data-quality checks (for analysts).
- [`monetisation.md`](monetisation.md) - operating AdSense.
- [`backlog.md`](backlog.md) - known data-quality issues and planned fixes.

If you're new to the project, start with the [README](../README.md) for the
tech stack and getting started, then come back here for the details that
aren't obvious from the code.

## 1. Versioning and `package-lock.json`

The project version lives in the `version` field of `package.json` - that is
the **single source of truth**. Bump it there; nothing else needs to change
by hand.

### After version bump: sync `package-lock.json`

`package-lock.json` mirrors the version automatically on `npm install`. After
bumping `package.json`, run:

```sh
npm install --package-lock-only
```

This rewrites the lockfile's `version` field (both the top-level one and the
one under `packages[""]`) to match `package.json`.
**Never hand-edit the lockfile's `version` field** - let npm do it.

Then **commit both files together**:

```sh
git add package.json package-lock.json
git commit -m "Bump version to X.Y.Z"
```

### Semantic versioning

Follow [semantic versioning](https://semver.org/):

- **patch** (e.g. `1.0.0` → `1.0.1`) for parser fixes, dependency updates, doc
  corrections, and other changes that don't alter the user-visible behaviour of
  the site or the data schema.
- **minor** (e.g. `1.0.0` → `1.1.0`) for new data sources, new dashboard
  features, or additive changes to the data schema.
- **major** (e.g. `1.0.0` → `2.0.0`) for breaking changes to the data schema,
  the site structure, or anything that requires users to update tooling that
  consumes the JSON.

The site footer reads the version via a JSON import in
`src/layouts/Dashboard.astro`, so a `package.json` bump is reflected on the
next `astro build` with no other change.

> The `version` field in `.vscode/launch.json` is the VS Code launch-config
> schema version, **not** the project version. Do not touch it when bumping
> the project.

## Local development workflow

The data build is **decoupled** from the site build:

```sh
# 1. Fetch real data once (slow - fetches live vendor sources)
npm run data:build

# 2. Iterate on the site freely - the dev server reads the JSON on disk
npm run dev
```

`astro build` only reads the pre-generated JSON in `src/data/`; it never
triggers scraping. So you can iterate on the website without re-downloading
data.

For fast iteration without real data, generate a small synthetic dataset:

```sh
npm run data:sample
```

### Dev server startup

The dev server can take **longer than 30 seconds** to start on the first run
because Vite needs to optimise dependencies (Tailwind v4, Svelte 5, D3).
**Do not use `astro dev --background`** - it has a hardcoded 30s timeout that
can fail before the server is ready. Use plain `npm run dev` (foreground).
Subsequent starts are faster once the Vite cache is warm.

## Frontend architecture

- **Astro 7** static site generation, with **Svelte 5 islands** for the
  interactive dashboard (hydrated controls + D3 charts).
- **D3.js** for chart rendering, wrapped in Svelte components.
- **Tailwind CSS v4** via `@tailwindcss/vite` (not `@astrojs/tailwind`).
- **Zod** for data validation.

### Design tokens (Tailwind v4)

Custom design tokens live in the `@theme` block in `src/styles/global.css`.
They're exposed as **both** Tailwind utilities (`bg-vt-bg-secondary`) and CSS
custom properties (`var(--vt-bg-secondary)`) for D3/SVG use.

**Gotcha:** in Tailwind v4, untitled (non-`@layer`) CSS rules outrank utility
classes. Wrap base-element rules in `@layer base { ... }` so the cascade order
is `base` → `components` → `utilities`, with untitled declarations at the
bottom.

### Manufacturer colours

`src/lib/manufacturers.ts` is the **single source of truth** for manufacturer
colours (`MANUFACTURERS` array + `getManufacturerColour()`).
`src/lib/d3/theme.ts` imports from it; `scripts/aggregate.ts` writes
`manufacturers.json` from it.

**Gotcha (dev desync):** the filter-chip dots and the charts must both read
colours via a **live import** from `manufacturers.ts`, not from the generated
`manufacturers.json`. The JSON is gitignored and only regenerated by
`npm run data:build`, so `npm run dev` never updates it - reading colours from
the JSON causes the dots and charts to desync on the dev server. Use
`getManufacturerColour(name)` for anything that should update on hot-reload.

## Key gotchas

These are the non-obvious traps that may trip the unwary. Each is verified
against the current code.

### Svelte 5 prop `null` vs `undefined`

When a Svelte component is wrapped by another Svelte component, the Astro >
Svelte island bridge can deliver an "omitted" prop as either `null` or
`undefined`, depending on the chain and destructure defaults.
**Use `== null` (loose) rather than `=== undefined`** when checking "was this
prop omitted". Treat both identically.

### D3 `stack()` data accessor

D3's `stack()` wraps data as `[y0, y1]` arrays; the original object is at
`d.data`. The area generator must use `d.data._date`, not `d._date`.

### Astro hyphenated content collections fail on Windows

Astro 7's glob loader silently fails to populate collections whose directory
name contains a **hyphen** on Windows. Use a camelCase collection key (e.g.
`chartExplanations`, not `chart-explanations`). Symptom: the first page
referencing the collection fails with "the collection does not exist or is
empty".

### `astro check` false positives

`astro check` reports false-positive Svelte 5 prop type errors; the actual build
works fine. Don't chase them.

### NVD API date parameters return 404

The NVD API 2.0 currently returns **404 for all date-range parameters**
(`pubStartDate`, `pubEndDate`, `lastModStartDate`) regardless of format,
combination, or API key. You **cannot** bound the NVD fetch by date to reduce
volume. `virtualMatchString` alone works (200). Do not re-add `pubStartDate`
until NVD fixes this.

### Dedup: no-CVE records dedupe by `id`

`deduplicateRecords` (`scripts/pipeline/normalise.ts`) keys every record by
`record.id` first, then by CVE id. Records without a CVE list have `id` as their
**only** identity. If your parser falls back to a date-based id (e.g.
`chrome-2026-07-15`), two records from the same date collide and the later one
is silently dropped.

**Fix:** for no-CVE fallback records, derive the id from a stable per-record
identifier - the post URL, advisory ID, or a hash of the URL. See
`scripts/pipeline/sources/chrome.ts` for the canonical pattern
(`createHash('sha256').update(url).digest('hex').slice(0, 12)`).

### MSRC Mariner catalog re-import

Microsoft publishes a separate CVRF document per advisory, including one per
**Mariner** (their Linux distribution) advisory, each referencing ~30 upstream
Linux CVEs. The `<vuln:RevisionHistory>` contains a single entry - the catalog
re-import date - not the upstream CVE's original publication date. The parser
must skip Mariner documents and per-vuln notes (see
`scripts/pipeline/sources/msrc.ts`), and the dedup's `dateMatchesCveYear`
sanity check drops records whose date is >1 year from any CVE-year.

**Symptom to watch for:** a single-month spike of 1,000+ records whose CVE-years
span decades but whose `discoveredDate` is recent. See
[`backlog.md`](backlog.md) §1 for the known residuals.

### Zod 4 API

Use `z.iso.datetime()` and `z.url()` instead of `z.string().datetime()` and
`z.string().url()`.

### `import.meta.url` in build-time loaders

During Astro build, `import.meta.url` may resolve to a Vite-internal path. Use
`process.cwd()` as a fallback to find the project root (see `src/lib/load.ts`).

### BacklogPoint uses `openCount`

`BacklogPoint` uses `openCount`, not `count`. `BacklogChart` maps it before
passing to `StackedAreaChart`.

## Testing

The pipeline tests run without a test framework - they use `node:assert` so we
get pass/fail output without adding a devDependency:

```sh
npm run data:test
```

This runs the dedup/date-sanity tests and the MSRC Mariner filter tests. Add new
test cases to the relevant `scripts/pipeline/test-*.mjs` file as new date
semantics or parser behaviours are added.

## Adding a new data source

The README has the 5-step checklist. The developer-specific gotchas to keep in
mind:

1. **Dedup identity** - if your parser produces no-CVE fallback records, hash
   the URL (see the dedup gotcha above), not a date.
2. **Colours** - add the manufacturer to `src/lib/manufacturers.ts` (single
   source of truth). Don't duplicate colour values elsewhere.
3. **Zero-record stubs** - if the source is a documented stub that always
   returns `[]`, add its `SourceId` to the `ZERO_RECORD_ALLOWLIST` set in
   `scripts/pipeline/index.ts` with a comment explaining why. Otherwise the
   silent-empty cache fallback will mask real progress when the stub is revived.
4. **Live-probe before fixing parsers** - always probe the actual endpoint
   before "fixing" a parser. A confident diagnosis can be wrong (the MSRC "JSON"
   endpoint actually returns CVRF XML).

## Data pipeline resilience

The pipeline has several safeguards so a scheduled publish doesn't deploy a
degraded site when sources fail:

1. **Defensive fetching** - all parsers go through
   `scripts/pipeline/fetch-with-retry.ts` (timeout, retry with backoff,
   retryable status codes 429/502/503/504).
2. **Cached fallback** - when a source fetch throws, the pipeline reuses the
   previous run's `src/data/raw/<source>.json` instead of overwriting with `[]`.
3. **Failure threshold** - the pipeline aborts if more than
   `MAX_SOURCE_FAILURES` (default 2) sources fail with no cached data.
4. **Silent-empty cache fallback** - a source returning 0 records when the
   previous run had data reuses the cache (with a warning), preventing
   unrecoverable data loss (since `src/data/*` is gitignored).

### Non-fatal `data:build` (timeout only)

In `scripts/publish.ts`, the `data:build` step is configured `fatal: false`,
but a step is only **non-fatal when it times out** (`err.code === 'ETIMEDOUT'`,
e.g. NVD is slow). On timeout the publish warns and continues with whatever
data is on disk — which may be a partial/mixed snapshot if the pipeline was
interrupted mid-write, not necessarily the previous run — so the deploy is not
blocked. The site may be one run stale.

Any genuine failure — a non-zero exit, a pipeline abort, a parser error — is
**still fatal** even with `fatal: false`, so real problems block the deploy. The
`runStep` helper prints the `nonFatalMessage` option so the warning text can be
tailored per step.

## Cross-platform `node_modules`

`node_modules/` is gitignored because some dependencies (notably `esbuild`)
ship a platform-specific native binary. **Run `npm ci` on each platform once**
(Windows, Linux/WSL, macOS) to install the correct binaries. After that, every
script that uses `tsx` is prefixed with `node scripts/check-platform.mjs &&`,
which auto-runs `npm ci` if the wrong-platform esbuild is present. See
[`publishing.md`](publishing.md) for the full detail.
